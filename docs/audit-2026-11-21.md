## 3. Honesty repairs

### 3.1 Vitals fabrication defect (fixed f845e3b, v0.3.8) [RUNTIME]

The actual defect, recovered from the pre-fix source: the manual vitals form
**opened pre-filled with normal values** ('120', '80', '98'), and on save it
converted blank or invalid input into normal-looking values via
`parseInt(x) || <default>`. An empty pulse became 72 bpm, an unreadable SpO2
became 98%. It then computed and stored a **clinical BP staging label**
('Normal', 'Elevated', 'Stage 1 HTN') on that fabricated self-reported data.

The fix: fields open blank with example-prefixed placeholders; blank,
whitespace, non-finite and non-positive inputs are rejected with errors and
never default-filled; only definitional guards remain (SpO2 ≤ 100, systolic ≥
diastolic); the staging chip is removed; saved entries are labeled
"Self-reported; not clinically reviewed". Residual caveat: v0.3.0–v0.3.7 APKs
still contain the old path; localStorage entries written by those builds are
provenance suspects, not proven fabrications. No stored data was deleted or
relabeled [CODE].

### 3.2 Report autofill interpretation (fixed 9bea117 + residual fix 6901329) [RUNTIME]

9bea117 removed the canned clinical interpretation from the sample-preset and
file-upload autofill actions. The final gap audit found a **residual instance
it missed**: the Upload Report modal's initial state still pre-filled
"HbA1c: 6.4% (Good Control)… Renal function intact." plus Telugu/Hindi advice
equivalents. A freshly opened modal therefore still carried fabricated
interpretation. Fixed in 6901329: initial values now match the honest
sample-only wording, verified by opening the real modal in the browser.

### 3.4 Wellness BP card: false ABHA success, no validation, band judgment on edits (fixed 3966829 + 43fa8c1, shipped v0.3.11) [RUNTIME]

Found tonight during the health-goals behavioral sweep. The manual Blood
Pressure & Pulse card in the patient portal's Health Goals tab had three
defects:

1. **Fabricated external-system success.** Tapping "Log Vitals Reading"
   toasted that the reading was recorded to ABHA (the national health ID
   system). No network write exists in that flow; the entry only lived in
   component state. The toast now reads that the value was noted for this
   demo session only and that nothing was saved or sent to ABHA.
2. **No input validation.** Blank, zero, negative and reversed
   systolic/diastolic values were accepted and toasted as success. The
   handler now rejects blank/whitespace, non-finite, zero/negative and
   reversed BP with an explicit error banner and logs nothing.
3. **Target-band judgments on edited readings.** The card issued a live
   threshold judgment on whatever numbers sat in the fields, recomputed on
   every keystroke: below 120/80 it read "In target band (sample)", otherwise
   "Above target band (sample)". Editing the sample defaults (118/78/72,
   sample data) to an out-of-range value therefore produced an above-target
   judgment on the user's own input, still tagged sample. After the fix,
   band judgments render only while the sample values are untouched; any
   edit swaps the badge to "Edited, not evaluated (demo)", and the resting
   pulse line drops its sample-value tag on edit.

Release boundary: **v0.3.10-debug and every earlier release contain the
defect**; the repair ships first in v0.3.11-debug. Browser-verified only; the
native shell is untested as in §7.

### 3.5 Sleep card frozen metrics and unlabeled praise alert (fixed a83ecf7, shipped v0.3.12) [RUNTIME]

Found by the wellness-cards probe after the BP repair, same honesty class:

1. **Frozen sample metrics on edited sleep hours.** The sleep card's +/-30m
   buttons edited the displayed duration, but the recovery metrics stayed
   frozen: "Score: 88/100", "Deep 24% (1h 48m)", "REM 22%", "Sleep Debt 0m",
   none of them sample-tagged (only the quality label read "Good (sample)").
   At 4.0 edited hours the card still claimed score 88 and 1h48m of deep
   sleep, and 1h48m is arithmetic that only holds for the 7.5h sample. The
   fix tracks edits: while the sample is untouched the score and breakdown
   carry sample-value tags; after any edit the badge swaps to "Edited, not
   evaluated (demo)", the score is hidden, and the breakdown is replaced by
   the same neutral note.
2. **Unlabeled fabricated praise.** The pillbox card's "Hear Praise in
   Telugu" button fired an alert with personalized clinician praise (a named
   demo doctor approving the user's medication routine) with no sample
   marking on the button or in the text. The button is now labeled "Play
   sample praise (Telugu, synthetic)" in all six locales, and the alert text
   opens with the locale sample tag.

Release boundary: **v0.3.11-debug and every earlier release contain both
defects**; the repair ships first in v0.3.12-debug. Browser-verified only;
the native shell is untested as in §7.

### 3.6 Join-button false liveness: dialogs, ACTIVE badge, teleconsult room labeling (fixed 38443ab + d1b3edc, shipped v0.3.13 + v0.3.14) [RUNTIME]

Found by an app-wide alert()-claim sweep:

1. **Fabricated session launch.** The home tab's Join button on the
   assigned-doctor card alerted that a video session was launching; nothing
   exists or starts. The appointments tab's Join Call button (teleconsult
   fixtures) alerted that a teleconsultation session was initialized with a
   secure WebRTC media bridge, fabricating both an initialization and a
   security property. Both now state (six locales): demo preview only, no
   video session was started, teleconsultation is not connected in this
   prototype. Ships in v0.3.13-debug; **v0.3.12-debug and every earlier
   release contain the false claims**.
2. **Liveness badge on a non-connected control.** The Join Call button
   carried a green ACTIVE chip implying a live call. It now shows a neutral
   sample chip, and the whole control reads "Join Call (sample)". Ships in
   v0.3.14-debug; **v0.3.13-debug and earlier contain the badge**.
3. **TeleconsultModal labeling.** The existing teleconsult room modal
   presented as a live call: green connected indicator, running call timer,
   synthetic doctor avatar cycling speaking/listening states, scripted
   bilingual captions, and an unprompted camera request for the selfie
   preview with no remote peer. It now opens with an amber DEMO chip and a
   banner stating the room is a local preview only, nothing is connected or
   transmitted, the doctor is a synthetic avatar with scripted captions, and
   the mic toggle does not capture audio. Ships in v0.3.14-debug.
   Reachability finding: the modal is currently dead UI. Its only opener is
   the Innovation Hub modal, whose trigger prop is never invoked by the
   navbar, so no user action can open the room (or trigger its camera
   request) in this build. The labeling is defense-in-depth; wiring decisions
   remain a product question.

### 3.7 Reports PDF button and manual med add: fabricated action claim, untagged local add (fixed 7c5c4ef, shipped v0.3.15) [RUNTIME]

Same alert()-claim sweep, two residuals on other surfaces:

1. **Fabricated PDF export.** Every report card's PDF button alerted
   "Preparing demo PDF copy of {title}...", claiming an export was underway;
   nothing is generated or downloaded. It now states (six locales): PDF
   export is not available in this build, no file was generated or
   downloaded. Ships in v0.3.15-debug; **v0.3.14-debug and every earlier
   release contain the fabricated preparing claim**.
2. **Untagged local medication add.** The manual Add Medication save alerted
   "{name} added to your chronotherapy schedule!", hardcoded in English, with
   no demo-only or no-persistence framing for a state-only (reload-losing)
   change. It now states (six locales, name interpolated): added to this
   demo schedule only, not saved permanently, no prescription record was
   created. Ships in v0.3.15-debug; **v0.3.14-debug and earlier contain the
   untagged English-only alert**.

Verified by pdf-med-notes-test.mjs (2 scenarios, both passing): dialog text
captured from the browser for both flows. Context note: report cards already
carry a static "Sample report data, not clinician-reviewed" subtitle for
every entry, which under-labels user-uploaded reports whose summary the user
edited with real content (conservative direction); making that subtitle
origin-aware is a parked refinement, not a defect with a false claim.

## 5. Accessibility & i18n: current state and residuals

Done [RUNTIME]: vitals form on react-hook-form (uncontrolled); invalid submit
focuses the first error field; per-field aria-invalid + aria-describedby
errors; validation messages via i18n keys; dictionary-parity test enforces
100% key completeness across en/te/hi/ta/kn/mr **for the keys that exist**;
global rule hides the assistant launcher while any modal is open (found by
hit-testing); scanner dark-panel contrast repaired (privacy badge, token-panel
heading, source badge) and swept for other dark-on-dark cases. Since the first
edition of this audit, the vitals modal's labels, recording-source options,
buttons, subtitle, saved-entry note and error-summary field names were moved to
26 new i18n keys across all 6 locales (commit 6d882a8) and runtime-verified in
Telugu: labels, options, per-field errors, focus-first-error and summary
bullets all render translated.

Known residuals [CODE]:

- Dictionary parity means key parity, **not** full translation coverage of the
  app and not any conformance claim. Forms outside the vitals modal (Upload
  Report, appointments, settings) still carry hardcoded English strings.
- Focus-first-error and per-field aria errors exist **only** on the vitals
  form; other forms have not been brought to the same standard.
- No automated axe-core conformance run is claimed as passed; ad-hoc probes
  were used.

## 6. LHC-Forms structured-intake pilot: assessed, deferred

Under the approved plan's conditional boundary ("if beyond medium effort,
defer"):

- **Fit concern, not a measured APK impact:** lforms@44.3.1 ships ~67 MB
  unpacked and lists jQuery, moment, zone.js and rxjs among its dependencies.
  What part of that would reach this app's bundle was **not measured**; the
  unpacked size is a distribution signal only.
- **No documented React adapter** was found in the package metadata/README
  reviewed tonight (integration would be an imperative DOM mount inside React).
  This is not an exhaustive claim about every version or community wrapper.
- **Unresolved obligations, not a legal prohibition:** the license is custom
  NLM/LHNCBC terms with LOINC (Regenstrief) and UCUM conditions layered on.
  Those terms were not fully evaluated tonight; the plan holds unresolved
  rights to link-only.
- Nothing was installed; no fixture was built; the quick-entry flow is
  untouched. A within-scope alternative (minimal native renderer for a small
  synthetic Questionnaire subset on the already-integrated react-hook-form)
  would need explicit approval before starting.
